# تصميم: مختبر الساندبوكس iOS (إطار تنفيذ الاختبارات)

التاريخ: 2026-11-20
الحالة: مسودة للمراجعة — لم يُوافق عليها بعد

## النية ولماذا
باحث أمني يريد أداة شخصية على **iPhone عادي (غير jailbroken)** لتنفيذ كود يكتبه بنفسه ومراقبة ما يسمح به ساندبوكس iOS فعلياً. القيمة ليست في درجة أمنية، بل في **رصد خام صادق**: ماذا أعاد النظام، بأي خطأ، وفي كم وقت. التطبيق إطار (framework/harness) فقط؛ **كود الاختبارات نفسه ليس جزءاً من هذا العمل**.

## الأهداف
1. توفير «ملف اختبار فارغ» جاهز ومُسمّى بعناية، يُوضع فيه كود المستخدم لاحقاً.
2. زر Run (و Run All) ينفّذ الكود الموجود في الملف ويلتقط النتيجة.
3. حفظ كل تنفيذ كسجل خام في **SwiftData** محلياً مع بيانات الجهاز/الإصدار/الزمن.
4. تنظيم الإطار بحيث إضافة «حالة اختبار» جديدة = ملف واحد، دون لمس الكود القائم.
5. البناء والتحقق الآلي عبر GitHub Actions على macOS runner.

## non-goals / حدود ثابتة
- **لا كتابة كود اختبار** من قِبل الوكيل؛ الملفات تبقى قوالب فارغة بعلامة إدراج واضحة.
- **لا تحميل كود وقت التشغيل**: على iOS غير jailbroken لا يمكن قراءة ملف كود خارجي وتنفيذه (Code Signing + W^X). الملف الفارغ يُترجم مع التطبيق؛ تعديله يتطلب إعادة بناء عبر Xcode.
- لا jailbreak، لا استغلال، لا تحايل على حمايات النظام، لا بيانات مستخدمين حقيقية، لا أسرار، لا إرسال شبكي.
- لا حالات قد تُسقط التطبيق (كتابة في ذاكرة تنفيذية، مؤشرات خاطئة)؛ كل حالة تستخدم APIs تُعيد خطأً بدل التحطم.
- لا درجة إجمالية ولا تصنيف «قوة الساندبوكس» (القرار: رصد خام فقط).
- لا محاكاة CI للحالات: Actions يبني ويشغّل اختبارات الوحدة فقط؛ الحالات تُشغَّل يدوياً على جهاز حقيقي.

## القيود
- SwiftUI + SwiftData، حد أدنى **iOS 17+**.
- البيئة المحلية Linux بلا Xcode؛ البناء الرسمي عبر GitHub Actions (`macos-*` runner).
- النتائج رصدية فقط: لا يمكن إثبات سلوك تحت jailbreak من جهاز نظيف.

## المدخلات التي قررها المستخدم
- الغرض: بحث في سلوك iOS والساندبوكس نفسه.
- تنفيذ الكود: كتالوج دوال Swift مترجمة مسبقاً.
- بنية الكتالوج: **سجل البروتوكول** (بروتوكول + ملف لكل حالة + سجل ثابت).
- البيئة: iPhone عادي غير jailbroken.
- التسجيل: SwiftData محلي، **رصد خام فقط** بلا توقعات مطابقة.
- الأبعاد الستة التي يجب أن يستوعبها الإطار كتصنيفات: نظام الملفات، العمليات والإقلاع، الذاكرة وحماية التنفيذ، تحميل المكتبات، الشبكة والمنافذ، الصلاحيات والـ entitlements.

## قرارات تفصيلية أُضيفت بعد مراجعة مستقلة
- **معرّف الجهاز والتاريخ**: يُحفظ `hw.machine` عبر `sysctl` (مثل `iPhone16,2`) لا `UIDevice.current.model` العام، مع إصدار iOS ورقم البناء، و**طابع زمني كامل لكل تشغيل**. السبب: تمييز الجهاز/الـ SoC ضروري لتفسير نتائج الساندبوكس (Secure Enclave، PAC…) وإعادة إنتاجها؛ والتاريخ مطلوب في السجل.
- **تفصيل الخطأ**: يُخزَّن `NSError.domain/code` وقيمة `errno` الأصلية إن وُجدت، إضافة إلى `localizedDescription` كنص مقروء. السبب: الفرق بين `EPERM` و`EACCES` جوهر الرصد الأمني، والوصف المُترجَم قد يخفيه.

## المقاربة المختارة (وسببها)
**سجل البروتوكول.** بديل مرفوض: `enum` مركزي بـ `switch` — أقل كود ابتداءً لكن كل حالة جديدة تلمس مُشغّلاً مركزياً ويتحول إلى ملف ضخم، بما يخالف قاعدة «التقسيم الاحترافي».

## شكل الإطار (ما سيبنيه المنفّذ لاحقاً)
```text
SandboxLab/
  App/                     // entrypoint + ModelContainer
  Domain/
    SecurityProbe.swift    // protocol: id, title, category, body() async throws -> String
    ProbeCategory.swift    // enum من 6 حالات (أسماء عربية للعرض)
    ProbeObservation.swift // القيمة الخام: نص + خطأ + زمن + بيانات الجهاز
  Registry/
    ProbeRegistry.swift    // [any SecurityProbe] ثابت — يحوي قالباً واحداً حالياً
  Runtime/
    ProbeRunner.swift      // قياس الزمن، والتقاط الأخطاء، بناء السجل، حفظه
    DeviceInfo.swift       // sysctl hw.machine، iOS، رقم البناء
  Storage/
    ProbeRun.swift         // @Model في SwiftData
  UI/
    ProbeListView.swift    // قائمة مجمّعة حسب التصنيف + زر Run / Run All
    RunDetailView.swift    // عرض النص الخام والخطأ والزمن
    LogListView.swift      // تصفح السجلات المحلية
  Probes/
    CustomProbe.swift      // ← الملف الفارغ: قالب يُوضع فيه كود المستخدم
```

عقد الملف الفارغ (هكذا سيبدو، بدون أي كود اختبار فعلي):
```swift
struct CustomProbe: SecurityProbe {
    let id = "custom"
    let title = "اختبار مخصص"
    let category: ProbeCategory = .filesystem

    func body() async throws -> String {
        // ← ضع كود الاختبار هنا
        return ""
    }
}
```
المسؤول عن الزمن والتقاط الأخطاء والتسجيل هو `ProbeRunner`، لا حالة الاختبار. القالب يُعيد نصاً خاماً أو يرمي خطأً؛ الإطار يسجّل الاثنين.

## ما يُترك للمنفّذ (مرحلة الخطة، لا هذه الوثيقة)
- تفاصيل الحزم/المجلدات الدقيقة واتفاقيات التسمية.
- طريقة قياس الزمن ومعالجة الإلغاء/المهلة.
- تصميم شاشات SwiftUI وطريقة تمرير `ModelContext`.
- إعداد مشروع Xcode، الـ target، والقدرات (capabilities) اللازمة.
- workflow ملف `ci.yml` على macOS runner: بناء + `xcodebuild test` لوحدة الإطار فقط.
- اختبارات الوحدة للإطار (registry، runner، التخزين) بحيث تعمل على CI دون جهاز.

## معايير القبول
- Adding a probe = ملف واحد جديد في `Probes/` + سطر في `ProbeRegistry.swift`، بلا تعديل Runner أو UI.
- الضغط على Run ينفّذ `body()` ويضيف سجلاً واحداً في SwiftData حتى لو رمى الخطأ.
- السجل يحتوي: معرّف الحالة، التصنيف، **الطابع الزمني الكامل للتشغيل**، المدة، النص الخام، والخطأ مُفصّلاً (`domain`، `code`، `errno` الخام، `localizedDescription`)، **معرّف العتاد من `sysctl(hw.machine)`**، إصدار iOS، رقم البناء.
- لا توجد أي قيمة حساسة أو إرسال شبكي في الإطار.
- يبني الـ workflow على macOS runner وينجح؛ الحالات لا تعمل على CI (متوقع).
